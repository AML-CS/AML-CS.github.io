PyTEDA-web

The web interface of TEDA: set up an ensemble data assimilation experiment in the browser, run it on the server, watch the error curves arrive live, and keep every run to compare later.

Above: how a run travels through PyTEDA-web. The browser talks to a FastAPI back end; TEDA does the assimilation; the models are Lorenz-96 inside TEDA, or QG-Python and swesphere installed next to it; PostgreSQL keeps every run.

What it is

TEDA is a Python library: you write a script, run it, and plot the errors. PyTEDA-web puts the same experiments behind a web page. You pick a model, one or more method instances (the same filter with different localization radii, say), an ensemble size, an observation network and a seed, and launch the run. The back end executes it with TEDA and streams the background and analysis errors to the browser step by step, so you see the filters diverge or converge while they run.

Nothing is lost when the page closes. Each run, its configuration and its results go to a PostgreSQL database, so a benchmark done today can be reopened, compared with another one, or downloaded as CSV weeks later.

Models

TEDA ships the Lorenz-96 system (40 variables, forcing F = 8), which is what the public demo runs. Larger models are not part of TEDA: they are separate packages that expose the same interface, a state vector and a propagate(x, [t0, t1]) call. Two are available today, both from this lab:

  • QG-Python: the 1.5-layer quasi-geostrophic model, 97 × 97 by default, with RK4 and Leapfrog integrators.
  • swesphere: the shallow-water equations on the rotating sphere, 66 × 132 and three fields, with documented flow regimes.

Install either one in the back end environment and it appears in the model list.

Methods

Every ensemble-based method of TEDA can be run: the stochastic EnKF, its Cholesky and modified Cholesky variants, the shrinkage precision estimator, B-localization, EnSRF, ETKF, LETKF and LEnKF. A run can hold several instances of a method with different parameters, which is how the platform is used for benchmarking.

Functionality

The front end uses the same HTTP API that scripts can call. These are the entry points of the back end.

EndpointWhat it does
GET /api/methodsthe assimilation methods available, with their parameters
GET /api/modelsthe models the server can run: Lorenz-96 (built in), QG-Python and swesphere when installed
POST /api/runscreate a run: model, method instances (for example LETKF with r = 1 and r = 2), ensemble size, observation setup, seed
GET /api/runsevery run stored in the database, with its configuration and status
GET /api/runs/{id}one run and its results
GET /api/runs/{id}/streamServer-Sent Events: background and analysis errors per assimilation step while the run is going
GET /api/runs/{id}/csvdownload the results as CSV

The interactive documentation of the API is served by FastAPI at /docs once the back end is running.

How it is put together

  • Front end: React 18 with Vite, charts in Plotly.js, served by Nginx.
  • Back end: FastAPI in Python. Creates runs, executes them through TEDA and streams results over Server-Sent Events.
  • Compute: the pyteda package (filters and Lorenz-96) plus any model package installed next to it.
  • Storage: PostgreSQL through asyncpg, holding runs, method instances and results.
  • Deployment: three Docker Compose services, frontend, backend and postgres.

Running it

git clone https://github.com/enino84/pyteda-web
cd pyteda-web
docker compose up --build        # then open http://localhost:3000

For development with hot reload, start only postgres and backend with Docker Compose, then npm install && npm run dev inside frontend/ (served at http://localhost:5173).
